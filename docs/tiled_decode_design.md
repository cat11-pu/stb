# 超大图分块解码设计方案（stb_image）

目标约束：

- 峰值内存 ≤ 原图数据（W×H×C 字节）的 20%
- 解码结果与全量解码逐像素一致
- 性能允许劣化，但不超过全量解码的 2 倍

## 0. 关键推论（先对齐前提）

- **20% 峰值 ⇒ 调用方不能持有整图缓冲。** 若调用方要求"整图一次性返回"，内存物理下限就是 100%，与 20% 矛盾。因此新接口必须是流式（按 strip 吐出）或区域式（只返回子矩形），现有 `stbi_load*` 保持原样。
- **逐像素一致 ⇒ 不改熵解码/滤波/IDCT 路径。** 分块只发生在"输出调度"层：同一套解码代码，差异仅限"是否写输出、是否做 IDCT/重采样"。这是像素一致性的结构性保证，而不是靠测试兜底。
- **≤2x ⇒ 以单遍顺序解码为主路径。** 任何需要多遍扫描压缩流的格式特性（Adam7、progressive JPEG）都直接出局，走回退。

## 1. 现状内存模型（代码依据）

| 格式 | 现状峰值 | 来源 |
|---|---|---|
| PNG | ≈ 2× 原图 | `stbi__do_zlib` 把全部 IDAT 一次性 inflate 到 raw 缓冲，`stbi__create_png_image` 再 unfilter 到输出缓冲，两者同时存活 |
| JPEG baseline | ≈ 1.5 B/px 分量平面 + 3 B/px 输出 | `load_jpeg_image` 按 MCU 解码进全图分量平面，最后逐分量重采样到输出 |
| JPEG progressive | ≈ 3 B/px 系数（short）+ 输出 | 全图 DCT 系数数组必须驻留到所有扫描结束 |
| GIF | 全画布 ×（1~2）+ 帧历史 | 帧间 disposal 依赖完整画布 |
| BMP/TGA/PNM | 输出缓冲本身 | 行式格式，天然可流式 |

## 2. 候选方案对比

### 方案 A：strip 流式解码（推荐主路径）

新增迭代器/回调式 API，解码器顺序解码一遍，每积累一个 strip（若干扫描行）就交给调用方。

- 内存：strip 缓冲 + 解码器状态。PNG 状态 = 2 行（unfilter 依赖上一行）+ 32KB deflate 窗口；JPEG 状态 = 1 个 MCU 行的系数。对任意大的图，峰值可压到远低于 20%（strip 高可调，预算硬顶时自动降低 strip 高）。
- 性能：PNG ≈ 1.0x（省掉全量 raw 缓冲的分配和写回，可能略快）；JPEG ≈ 1.0–1.1x。
- 一致性：熵解码路径零改动，风险最低。

### 方案 B：区域解码 `stbi_load_region(x, y, w, h)`

在 A 之上实现：顺序扫描，区域外的行解码后丢弃；JPEG 对区域外 MCU 只做熵解码维持 DC 预测链，跳过 IDCT/重采样/输出（这是耗时大头，跳过反而比全量快）。

- 内存 ≈ 区域大小 + 状态。区域 ≤ 20% 时达标。
- 性能：单区域 < 1x；**多个分散小区域必须合并为单遍扫描**（按行区间并集），否则 N 个区域 = N 遍解码，直接击穿 2x 预算。
- 横向裁剪注意：PNG 的 Sub/Paeth 滤波依赖行内左像素，JPEG 的 MCU 依赖左侧 DC 链，所以横向不能"跳过不解码"，只能"解码后丢弃"——成本小，但要在文档里写清，避免评审时误判为可横向随机访问。

### 方案 C：真随机访问 tile（不推荐）

只有带 RSTn 重启标记的 JPEG 支持按 MCU 行随机定位；PNG/BMP 无索引结构，需预扫描建索引（额外一遍 + 索引存储）。复杂度显著高于 A/B，收益仅限"反复随机读同一文件"的冷门场景。结论：不做；JPEG+RST 可作为后续优化项，不影响接口设计。

**推荐：A 为主路径，B 作为 A 的过滤包装，C 放弃。**

## 3. 分块边界与压缩流对齐

| 格式 | 最小分块粒度 | 对齐约束 | 分块方式 |
|---|---|---|---|
| PNG（非交错） | 1 扫描行 | unfilter 依赖上一行（Up/Avg/Paeth）⇒ 行是天然边界；行内因 Sub/Paeth 不可横切 | strip 高任意；横向裁剪在 unfilter 后丢弃 |
| PNG（Adam7） | 不可分块 | 像素终值第 7 遍才确定 | 回退（见 §6） |
| JPEG baseline | MCU（8 或 16 px，取决于采样因子） | tile 边界对齐 MCU 网格才能跳过 IDCT；非对齐裁剪在拷贝阶段做；无 RST 时 DC 链要求顺序熵解码 | strip 高 = MCU 行高的整数倍，最小 16 行 |
| JPEG progressive | 不可分块 | 全图系数驻留 | 回退 |
| BMP | 1 行 | 行 4 字节对齐、自底向上 | 天然可 seek，直接支持区域 |
| TGA | 1 行（RLE 包可跨行） | RLE 需顺序解码 | 流式可行，区域靠丢弃 |
| GIF | 整帧 | LZW 流 + 帧间 disposal | 仅逐帧流式，不支持区域 |

## 4. 渐进式解码可行性

- **JPEG progressive：不可行。** 多轮扫描细化同一批系数，全图 short 系数数组（≈ 3 B/px）必须驻留，与 20% 硬约束直接冲突。检测 SOF2 后走回退。
- **PNG Adam7：不可行。** 单遍 inflate 无法按行产出终值；两遍法要求输入可重读且 inflate 成本 ×7，远超 2x 预算。检测 interlace 位后走回退。
- **GIF 动画：天然渐进**，逐帧吐出即可，可支持。
- 结论：渐进式不作为主路径，格式检测后显式回退，不做"尽力而为"的半支持。

## 5. 与现有接口的兼容

- 现有 `stbi_load*` / `stbi_info*` 零改动，分块能力全部走新增 API：
  - `stbi_decode_caps(...)`：查询是否可流式/可区域/建议 strip 高（调用方先查后用，避免试错）。
  - strip 迭代器或回调（`next_strip` / 行回调）。
  - `stbi_load_region(...)`。
- `req_comp`、16-bit、HDR→LDR 转换在 strip 边界内逐 strip 应用，与全量路径共用同一转换函数，保证一致。
- **`stbi_set_flip_vertically_on_load` 与流式输出冲突**：翻转要求最后的数据先吐，等于要缓冲全图。决策：流式模式下检测到全局 flip 置位时返回显式错误（并在 caps 里体现），由调用方自行翻转；绝不在内部静默缓冲。
- 错误报告沿用 `stbi_failure_reason`（已有 `STBI_THREAD_LOCAL` 处理），新增回退类错误码（如 `STBI_ERR_FALLBACK`），语义为"本图不能分块，可选择全量解码（接受内存峰值）或放弃"。

## 6. 异常数据回退策略

- **截断/损坏流**：在与全量解码相同的位置报错；已吐出的 strip 前缀标记为部分结果，由调用方丢弃；strip 缓冲先清零再填，保证不泄露未初始化内存、不越界。
- **尺寸炸弹**：沿用现有 `stbi__mad4sizes_valid` 在 header 阶段拒绝，分块路径不放宽。
- **不支持的组合**（progressive JPEG、Adam7、GIF 区域、flip+流式、超宽图单行即超预算）：返回显式回退错误码，**禁止静默切换解码路径**（静默换路径是像素不一致的最大隐患）。
- **预算硬顶**：strip 高 × 行宽 × 通道超预算时自动降 strip 高；JPEG 受 MCU 对齐约束最小 16 行，若 16 行仍超预算（超宽图）则回退。
- **一致性兜底**：分块与全量共用熵解码函数，差异仅限输出调度；用同一语料做逐像素回归（`tests/pngsuite` + 自备大 JPEG/BMP/TGA），strip 高扫描 {1, 7, 16, 1000, H} 全等才算通过。

## 7. 风险清单

| 等级 | 风险 | 缓解 |
|---|---|---|
| 高 | 回退路径（progressive/Adam7）仍有全量内存峰值，用户可能误以为"所有图都 ≤20%" | caps 查询前置 + 文档和错误码明确契约；回退是显式选择而非默认行为 |
| 中 | JPEG "丢弃 MCU" 分支是新代码路径，跳过 IDCT 的边界条件（采样因子、restart 间隔、EOB 处理）易错 | 复用现有 oss-fuzz 基建（`tests/ossfuzz.sh`）对分块入口 fuzz；MCU 对齐单测 |
| 中 | 多区域请求若未合并单遍，时间复杂度 O(N×全图)，击穿 2x | API 层强制区域并集为单遍扫描；文档禁止逐区域循环调用 |
| 中 | flip/16bit/HDR/req_comp 与 strip 的组合爆炸 | caps 显式声明支持矩阵，不支持的组合报错而非隐式降级 |
| 低 | TGA RLE 跨行包在 strip 边界处的状态保存 | strip 边界不切断 RLE 包，按包解码、按行吐出 |
| 低 | 性能回归主要来自额外函数调度，预期 ≤1.2x，余量充足 | 基准语料回归，阈值 2x 告警 |

## 8. 验证计划

1. 逐像素：分块结果 vs 全量结果，全格式 × 多 strip 高 × req_comp 组合。
2. 峰值内存：用 `STBI_MALLOC`/`STBI_FREE` 计数钩子统计峰值，断言 ≤ 20%。
3. 性能：基准语料（大 PNG/JPEG/BMP/TGA），全量 vs 分块耗时比 ≤ 2。
4. 异常：pngsuite 损坏用例 + 截断流 + 尺寸炸弹，验证报错位置与全量一致、无部分结果泄漏。
5. fuzz：分块入口接入现有 oss-fuzz 流程。
